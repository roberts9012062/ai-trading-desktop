# 加密货币本地因子与算子优化研究

日期：2026-09-25。范围：超级因子挖掘、因子实验室的本地 CPU / GPU 路径。
本次是代码研究与小规模复核，未修改生产计算逻辑，未进行真实行情收益或性能基准测试。

## 结论

两处页面共用因子内核，应建设一套加密货币研究配置，由两个入口调用。
优先顺序：修正市场口径 → 剔除不可用特征 → 增加有效信息 → 优化算子搜索与执行。
当前主要问题不是算子数量不足，而是期货时间语义、现货数据与永续评估口径混用，以及无效搜索空间。

## 1. 两处入口与共同改动点

| 入口 | 调用链 | 特有改动 |
|---|---|---|
| 超级因子挖掘 | `super-factor-page.tsx` → `mining/local-runner.ts` → CPU/GPU backend → Python 因子内核 | 将市场类型、特征配置、算子配置、数据版本写入任务和冻结快照，恢复时校验 |
| 因子实验室 | `use-factor-lab-page.ts` → `local-factor.ts` → CPU 步进会话或同一 GpuBackend | 搜索、LLM 种子、进化、单因子回测、组合评估传递相同配置 |

共同核心：`public/pykernel/factor_lab/{features,ops,vm,search}.py`、`scoring/`、
`public/pykernel/factor_local.py`，以及 `src/lib/mining/gpu/`。
已有特征矩阵缓存、GPU 排名缓存、会话复用、双缓冲读回、增强进化和增强遴选；不需要重新实现这些机制。
两个页面的本地增强开关默认均为开启，不能把增强遴选当成尚未提供的功能。

## 2. 已确认的问题

### P0：年化与时间特征仍使用国内期货口径

- `scoring/periods.py`：`TRADING_DAYS_PER_YEAR=243`，`distinct_trading_days` 使用期货交易日归属。
- `features.py`：TOD 使用 21:00～次日 15:00 的 18 小时时段；NIGHT 使用国内夜盘定义。
- DOW 使用 `(weekday-2)/2`，周六为 1.5、周日为 2，超出注释宣称的 [-1,1]。
- 这同时影响两处入口及 CPU/GPU，因为 GPU 的特征和年化基数由 Python 内核提供。

复核：本机 Python + NumPy，构造 2026-09-01 起连续 14 天、336 根小时线：

| 项目 | 实际输出 | 加密配置预期 |
|---|---:|---|
| 日线年化 | 243 | 采用明确的 365 天年化约定 |
| 小时线年化 | 7423 | 完整规则小时线按 8760；缺失行情另行检查 |
| DOW 范围 | [-1,2] | 七天周期编码 |
| 15～20 点 TOD | 全部为 1 | 24 小时连续周期编码 |

建议：新增显式 market/instrument 配置，统一传入年化、时间特征和评估函数。
新增 UTC 小时 sin/cos、七天星期 sin/cos、周末标记；币圈新搜索禁用旧 TOD/NIGHT/DOW。
旧 token 的含义不原地替换，旧公式回放保留原特征版本。

### P0：默认现货数据，默认永续成本，多空交易假设未分离

- `src/lib/kline-channels.ts` 默认 `binance_spot`。
- `data/product_specs.py` 的加密规格为 USDT 永续，默认单边费率 0.0005。
- `factor_local.resolve_cost()` 根据符号和价格推导静态成本，不识别交易所、现货/永续、maker/taker；没有资金费率时间序列。
- `KlineBar` 当前没有 funding、mark/index、主动买卖量等研究字段。

建议拆分 `crypto_spot` 与 `crypto_perp`：

- 无借币的现货使用多头/空仓收益口径；现货研究信号可以迁移永续，但必须重新用目标合约行情与成本验证。
- 永续按合约行情计算收益，并按实际结算事件计提资金费用，不能每根 K 线重复扣一次 funding。
- 手续费按交易所与执行方式配置；滑点支持 bp/流动性压力情景，不能只依赖一个 tick。
- 成本场景在搜索前固定。当前默认成本使用全段后部价格的中位数，建议训练成本改用事前固定值或训练段估计，减少训练口径对后段数据的依赖。

### P1：7 个缺失 OI 特征仍占用搜索概率

当前共 40 个特征、40 个算子。Binance 现货适配器明确输出 `open_interest: null`。
以下 7 个特征因此为零：OI_CHG、OI_PV、VOL_OI、OI_PC、OI_CHG5、OI_CHG20、VOL_OI_MA。
Python `_random_tree` 与 TS `randomTree` 均按全部特征 ID 均匀抽样，没有可用性掩码。
因此在默认无 OI 的数据上，17.5% 的叶子抽样概率落到这 7 个零特征；这不是整体算力浪费比例。

建议：仅用训练段和数据能力元信息计算 active_feature_ids，并统一应用于初始化、变异、重启和种子校验。
保留原始特征 ID 与完整矩阵行序，不能压缩后重新编号。
历史公式依赖缺失数据时明确标记不可执行，不把缺失 funding/OI 伪装为真实零值。

### P1：预热长度和归一化配置缺少完整的因果契约

- 特征归一化窗口下限由整段 `len(bars)/distinct_trading_days(bars)` 推导，窗口大小依赖传入段。
- `walk_forward.py` 固定 `WARMUP_BARS=250`；特征窗口在分钟加密数据上可能约为一天甚至因期货日期映射而更大。
- 嵌套时序算子还会增加历史需求，250 根并不能普遍保证与连续执行一致。
- VM `_normalize_output` 还用整段标准差决定是否绕过归一化，需要增加前缀不变性专项验证。

建议：按市场和 timeframe 明确冻结归一化窗口；根据表达式 DAG 计算累积 lookback，并计入特征与最终归一化。
EMA 的历史依赖不能简单视为有限窗口，应使用连续状态或声明误差容限与 burn-in。
验收必须比较“只输入截至 t 的数据”与“输入完整历史后截取截至 t”的共同有效输出。

### P1：封存段在逐代报告中反复评估

`search_stepwise` 每代调用 `_dedup_top`；增强遴选的 `_enrich_v2` 又计算 `holdout_metrics`。
GPU 每代精算也进入冠军遴选。因此代码注释中的“最终评估一次”，实际是每次遴选都会触发报告计算。
目前未发现该 holdout 数值直接进入遗传适应度；不能据此断言自动进化已泄漏。
但反复报告会让人根据封存表现停止、调参或重跑，失去真正的最终盲测属性。

建议：逐代只返回训练/验证指标，搜索冻结最终候选后才揭示封存结果；继续调参必须使用新的封存区间。

## 3. 因子优化：分两批引入

### 第一批：基于已有 OHLCV 即可落地

| 因子族 | 研究方向 | 注意点 |
|---|---|---|
| 24/7 日历 | UTC 日内周期、七天周期、周末交互 | 统一从原始时间戳转 UTC，当前前端时间字符串采用北京时间 |
| 波动调整动量 | 多尺度收益 / 实现波动率 | 已有 RET、ATR、STD，先做种子模板和组合消融，避免重复新增 |
| 冲击与流动性代理 | 绝对收益 / 成交额、放量冲击后的延续或反转 | close×volume 仅是成交额近似；不是盘口冲击实测 |
| 尾部与跳跃代理 | 极端收益占比、下行半方差、超阈值收益持续性 | 已有 SKEW/KURT/UPDOWN_VOL_RATIO，验证新增信息是否独立 |
| 成交结构 | 收益方向 × 相对量、量价背离、VWAP 偏离回归 | 已有 VWAP_DEV、PV_CORR，可优先构建短表达式种子 |

窗口不宜一律 5/20/60 根。可定义 1h、4h、1d 等经济时间候选，再按周期换算；
日线及样本不足时禁用不适用窗口。配置必须随公式持久化，不能让同一个旧 token 随配置静默改变语义。

### 第二批：接入额外数据后才有效

| 数据 | 因子候选 | 核心约束 |
|---|---|---|
| 主动买量/卖量、成交笔数、成交额 | 买卖不平衡、累积主动成交差、平均成交规模 | 保留交易所原始单位与字段，按数据源能力启用 |
| 历史 funding | funding 水平、变化、极端拥挤、结算时点交互 | 区分预测值与已实现值，只使用决策时已公布数据 |
| OI | OI 变化与价格/量联合变化 | 明确数量/张数/美元计价；限时前填，记录数据年龄 |
| 标记价/指数价/合约价 | 基差及偏离回归 | 同时点对齐，不能混用不同场所不同合约 |
| BTC/ETH 同步行情 | 市场残差动量、滚动 beta、领涨滞后 | 当前跨币验证不是跨币特征输入；新增输入要做时间对齐 |
| 盘口/逐笔/清算 | 盘口不平衡、订单流、清算冲击 | 需要历史采集与存储，OHLCV 无法可靠还原 |

以上均是待验证假设，未证明具有超额收益。优先做数据覆盖率和增量贡献评估，再扩大搜索。

## 4. 算子优化

### 搜索质量

1. 可用特征掩码优先于扩容；再按动量、反转、量能、波动、日历分配抽样权重，保留探索概率。
2. 增加少量中心化秩、稳健归一化、衰减加权等候选算子。旧 TS_RANK 保留原语义；新秩应明确相同值的中秩规则。
3. 当前已有 STEP、LAG、CORR、BETA、RESID、EMA，不应作为“新增算子”重复开发。
4. 定义返回值范围、量纲、缺失值、分母接近零、预热和复杂度等算子元数据；条件类表达式优先评估简单模板，暂不为 IF 强行扩展当前一元/二元 GP。
5. 做结构及行为去重。交换律规范化要考虑 f32/f64 数值容差，不能对浮点表达式随意重结合。
6. 对长度和昂贵窗口施加温和复杂度预算，记录有效候选率、克隆率、特征族覆盖与独立冠军数。

### 执行效率

- CPU 训练评估目前逐树执行；可增加任务级 tokens→训练指标缓存，并在有收益的情况下复用重复子表达式。
- CORR/BETA/RESID 当前使用滑动窗口和中心化二维临时数组；长窗口时评估 O(T) 滚动矩实现，但须解决消减误差并对拍。
- GPU 优化长窗口应依据实际 profiler；考虑 prefix sum / scan 和公共子式缓存，同时计入额外显存、同步及调度成本。
- GPU 当前排除 EMA，CPU 支持 EMA，因此两者的随机搜索空间并不相同。短期展示能力差异并保留 CPU 处理种子；长期再评估并行 scan 或混合候选池。
- Python 算子表、TS token 表、WGSL 实现目前需手工同步。建议由单一 schema 生成 ID/名称/元数/窗口及支持能力，并对每个实现做数值一致性验证。
- 不以 GPU 利用率作为唯一验收指标。更重要的是端到端耗时、每秒唯一有效候选、CPU 精算开销及粗排 top-K 召回率。

## 5. 兼容与数据契约

建议统一配置：market_type、signal_channel、execution_instrument、feature_profile、operator_profile、
normalization_profile、cost_model、calendar_version、data_snapshot_hash、kernel_version。

- 特征 ID 空间冻结为 0～63，当前使用 40 个，剩余 24 个；算子从 64 起。新增只能追加，不能移动旧 ID。
- 新特征建议先建立版本化研究配置，避免把有限 ID 全耗在同一公式的不同窗口上。
- 缓存键包含数据版本、配置版本与外部特征版本；funding/OI/跨币行情也必须进入冻结快照和哈希。
- 新增本地 token 必须贯穿公式展示、历史、收藏、LLM 词表、导出和本地实盘；服务端能力不足时沿用明确的本地专属限制。
- 两处页面都展示“现货/永续、实际启用特征、缺失数据、成本和验证区间”，默认配置来自同一模块。

## 6. 建议实施顺序与验收

第一阶段：统一加密市场配置；修正年化/时间；实现特征掩码；修正预热与最终封存揭示；两处入口参数一致。
第二阶段：补充 OHLCV 因子模板、少量算子、能力元数据、训练评估去重缓存。
第三阶段：保留主动成交字段，再接 funding/OI/基差/BTC 因子；数据范围由实际接口和本地积累决定。

验收采用固定真实行情快照、多个币种/周期与多个随机种子，分别比较：

1. 旧版基线；
2. 仅市场口径修正；
3. 再加特征掩码；
4. 再加因子/算子；
5. 最后加计算优化。

每组记录封存期净表现、换手、回撤、因子相关性、成本压力敏感性和跨币稳定性；
同时记录端到端耗时、峰值内存、有效候选率、GPU 粗排召回率。
不能用修正年化造成的数字变化冒充收益提升，不能用不同搜索空间的结果宣称 CPU/GPU 数值等价。
旧 token 回放、前缀不变性、CPU/GPU 算子对拍、两入口参数贯通、快照恢复和历史版本隔离应成为回归检查。

## 7. 本次验证边界

已完成代码追踪和合成数据数值复核；尚未跑真实行情消融、完整搜索性能基准或收益验证。
网络检索工具连接失败，外部接口细节以随后能核验的交易所官方文档为准；本报告核心问题均来自本地代码。
