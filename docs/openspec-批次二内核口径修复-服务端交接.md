## 五点六复测(2026-09-01 21:00):服务端已部分修复,死链还剩最后一环(纯服务端)

**背景**:服务端 19:24 重建镜像响应了上节——分期主力日历查询异常路径加了
warning 日志,且**空锚点**的边界请求已能拼出深历史(end_time=2026-04-16 13:30
→500 根至 2026-03-12,续翻→2026-01-28,has_more=true),`_fetch_dominant_minute`
本身已工作。但常规翻页(桌面端路径)仍停在 2026-04-16,复测定位到两处新根因。

**根因 1:拼接触发条件把"窗口贴边"误判为已覆盖**(`fetch_tickdata_kline` 分期
主力拼接分支)。翻到批次边界页(锚点 end_time=2026-07-02 10:45)时:
- lookback 窗口 start_dt ≈ 2026-07-02 − 76.9 天 ≈ **2026-04-16 13:00**(恰好贴着批次段起点);
- own bars = 202 根(2026-04-16 13:30~04-29)< n=500;
- `uncovered = first_ts is None or (first_ts − start_dt) > 2 天` → 首 bar 距窗口起点
  仅 30 分钟 → **False,拼接被跳过**;
- 该页 202<500 → `api/kline.py` 的 `has_more = len(bars) >= limit` → **False** → 翻页终止。

即"首 bar 贴着窗口边缘"恰恰说明更老数据被窗口截断,与"窗口中部有洞"一样需要
拼接——短页(len(bars)<n)本身就是 own 数据在窗口内耗尽的信号。
**但只取反 uncovered 还不够**:该页若触发拼接,日历查询窗口是 [start_dt≈04-16 13:00,
first_ts=04-16 13:30),仅 30 分钟 → 日历为空,仍拼不出。
**建议修法(二选一)**:
1. 短页填满:own+cont 后仍 len(bars)<n 时,以"补足缺口所需天数"
   ((n−len)/每日根数×1.5+缓冲)向前扩展拼接查询的 start 下界,直到填满 n 根
   或真无更老数据——页面不变式变为"除非真到底,每页总是满页",has_more 语义无需动;
2. has_more 信号修复:tickdata 返回"窗口截断 vs 真耗尽"标记,截断时短页也置
   has_more=true(桌面端下一页会锚定 2026-04-16 13:30,该锚点已实测可拼接续翻)。
方案 1 不动 API 契约,推荐。

**根因 2:连续合约 2026-05/06 两个月数据空洞**(pg-tickdata 直查月度行数):
rb9999 15m 有 2025-08~2026-04(483/498/391/460/521/460/314/506/452 根/月,
9998 与 9999 同值、8888 自 2025-10),**2026-05/06 为 0 行**;近期源(main db)
分钟最早 2026-07-02 10:45 → 04-30~07-01 两个月无任何来源。锚点落在空洞月
(end_time=05-15/06-01)的请求直接跳洞返回 2026-03-25~04-29,空洞对翻页不可见
→ 桌面端拼出的序列含 2 个月内洞;多段随机分段落进洞内会得到 0 bar 段
(0.1.33 修过的"全 0 段"以新形态复发)。建议批次补灌 2026-05/06 的
9998/9999/8888(具体合约数据齐全,可由分期主力拼接生成)或拼接逻辑支持前向洞填补。

**桌面端结论(复测确认)**:fetchBacktestBars 翻页/多段守卫行为全部正确,错误信息
如实呈现服务端边界,本问题纯服务端、桌面端无需改动。拼接修好后 15m 深回溯
