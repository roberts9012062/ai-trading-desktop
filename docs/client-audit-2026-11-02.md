## 需要处理的问题

### 1. P1：服务器模式缺少下单请求的持久身份与未知结果防重

位置：`src/lib/live-api.ts:354`、`src/lib/local-desktop.ts:51`、
`src/lib/local-order-intent.ts:16`。
配套服务端：`D:/pyobj/Decentralized transactions/backend/app/api/live.py:216`，
`backend/app/services/live_trading.py:494`。

服务器账户模式下 `localLiveBinding()` 返回 null，`placeLiveOrderApi()` 因而绕过
`withLocalOrderIntent`，直接发送不含 `client_request_id` 的 HTTP 下单请求。
该服务端入口也未接收稳定客户端请求号，后续每次生成新的 `client_order_id`。

复现：用模拟 fetch 记录“服务端已接收但响应丢失”的第一次请求，再模拟用户
手动重试同一输入。客户端发送两次，两次都没有稳定请求号，本机待核对记录为零。
没有任何真实金融网络请求。这里不是自动重试，而是响应未知后用户再次点击的风险。

影响：恢复服务器模式交易后，可能把同一操作当作两笔新订单；也缺少与本机
执行通道相同的“未知结果先核对”保护。

建议：为服务器模式同样保留稳定请求号、持久待核对状态和原单查询；服务端
接收并持久校验该请求号，建立唯一约束和终态回执。仅修改前端提示不足以防重。
该项应在重新开放服务器模式金融写入前完成。

### 2. P2：工作台的今日盈亏与风险率存在错误映射

位置：`src/lib/live-api.ts:184`、`:191`、`:195`；
`src/components/dashboard/asset-summary.tsx:55`、`:60`。

当前把 `raw.unrealized_pnl` 同时映射为浮动盈亏和今日盈亏，并把风险率固定成 0。
界面又以“今日盈亏”和百分比风险率展示这些值。余额还被映射为可用保证金，
持仓占用则以总权益减可用保证金推算；这些字段并非对应的完整交易所指标。

复现：模拟总权益 1000、可用 700、浮盈 50，映射结果为今日盈亏 50、风险率 0%、
余额 700、持仓占用 300，全程没有请求今日账单或实际风险字段。

影响：今日已实现损益、手续费及资金费不会反映在顶部今日指标中，风险率 0%
容易被理解为真实账户风险状态。单机和服务器账户都会经过这层映射。

建议：独立接入每日账单汇总与交易所实际账户字段；明确现金余额、可用保证金、
占用和风险指标的口径。无法取得的字段显示“未提供/待计算”，不补成虚假的零值。

### 3. P2：长时间断线后的 K 线尾部补齐会遗漏中间缺口

位置：`src/lib/collection-chart-cache.ts:41`、`:49`；
启动核对复用规则见同文件 `:74`—`:78`。

快速缓存刷新把尾部下载量限制为 500，随后直接合并缓存与最新数据，只检查
返回 K 线字段和最新时间，没有检查合并后是否连续。启动全量核对则按当前会话
复用已经完成的 promise，长时间断线重连并不保证重新跑这次深度核对。

复现：缓存停在 600 分钟以前，调用分钟图刷新，下载最新 500 根后仍有 100 分钟
缺口，但函数成功返回。使用 fake IndexedDB 和模拟行情，没有请求真实行情接口。

影响：程序长时间运行并经历较长断网后，图表可以显示最新价格，但中间历史
仍不完整，后续图表和指标会继续使用存在缺口的数据，直到另有深度补齐任务完成。

建议：保留“启动一次完整核对、切换直接读缓存”的交互；超过单页的尾部缺口
按范围分批追加下载，并检查连续性。缺口未补完时保留明确状态，不将它标为完整。

### 4. P2：Zod 锁定版本存在 high 级依赖安全记录

位置：`package.json:53`，锁文件解析为 `zod@4.4.3`。

官方 npm 审计返回 GHSA-mrhx-c7xc-m3w5：受影响范围 `<4.6.6`，修复版本 `4.6.6`。
问题涉及超大集合校验造成过量错误对象分配和内存耗尽。
[GitHub Reviewed 公告](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)。

本轮源码搜索没有发现业务代码直接导入 Zod，未证实当前客户端存在可触发路径。
因此这是一条已确认的依赖版本记录，不等同已经证明客户端能被远程攻击。

建议：核查是否仍需要该依赖；不使用则删除，使用则升级至修复版本并完成锁文件
与兼容性回归。不要为了清除审计数字盲目升级全部依赖。

## 优化建议

1. **首启缓存预热**：当前最多 60 合约 × 7 周期，共 420 个串行核对条目，条目
   内还有历史分页。首启后台可能耗时较长。建议按当前可见合约优先、冷热分层，
   在套餐配额内分阶段完成；不恢复“每次切换都全量核对”的旧交互。本轮没有测量
   不同用户网络下的真实预热耗时，不给出未经测量的秒数承诺。
2. **路由按需加载**：`src/router.tsx:21` 起同步导入研究、回测、行情和管理页面。
   主入口 JS 约 2.78 MB，gzip 约 0.85 MB。建议使用页面级懒加载，优先加载登录和
   当前页面，降低启动解析及首次渲染成本；构建体积告警本身不是构建失败。
3. **线路说明与离线能力提示**：`src/components/dashboard/announcement-bar.tsx:12`
   的提示只检查行情 provider，没有检查个人账户来源。服务器账户模式下仍可能
   显示账户由中心/本机提供。建议将行情线路和个人账户来源分开显示，并为任务、
   商城等依赖业务服务器的入口显示明确可用性。
4. **安全加固**：`src-tauri/tauri.conf.json:25` 的 CSP 为 null，默认 HTTP 能力
   放行全部 HTTP/HTTPS 目的地；多账号刷新令牌保存在 WebView localStorage。
   建议增加兼容自定义服务器/模型供应商的 CSP 与连接约束，将长期刷新令牌迁入
   原生受保护存储。本轮未发现可复现的脚本注入入口，这里属于防护层优化，不能
   表述成已确认的远程代码执行漏洞。

## 保持有效的边界与检查结果

- 新启动仍经过登录页，本机离线会话的创建/重启任务限制有现有回归覆盖。
- 单机账户配置、读取与服务器账户来源分离；未绑定账户的金融操作由原生入口
  拒绝，未在本轮发现其自动开通交易权限的问题。
- 中心 Key 故障不静默切回 OKX，按账号隔离的配置和 DPAPI 密封路径仍保留。
- 本机下单/人工操作的稳定请求号、执行权、原单核对和固定运行器校验保留。
- 路由与菜单没有新增猎手调度入口，相关禁用测试通过。
- 更新产物仍使用固定公钥验证；本轮未改更新渠道或发布版本。

优先顺序：先处理服务器模式金融请求防重，再修正资产指标与长断线缓存完整性；
随后清理依赖安全记录，最后分批做启动性能、提示一致性和安全加固。
